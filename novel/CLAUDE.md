# 長編小説をClaudeで書くための方法論

このドキュメントは、`novel/`配下の100万文字超の異世界転生小説（`isekai_novel_full.md`、全100章+幕間18編）を実際に生成した経験から得た知見をまとめたものである。目的は2つ:

1. Claudeで長編小説を書く際に「気づけば短く・要約的にまとまってしまう」問題を回避するための、再現可能な技術体系を残すこと
2. この手法によって具体的に突破できた、Claude(LLM)の構造的な限界を明文化すること

将来、同種の長編小説生成タスクに取り組む際は、まずこのドキュメントを読むこと。

## 前提: なぜ「コンパクトにまとまってしまう」のか

LLMに「長編小説を書いて」と指示すると、放っておくと以下の理由で必ず短く・要約的に収束する。

- **単一ターン・単一コンテキストの出力には実務上の上限がある**: 1回の応答で数万〜十万文字を超える生成は現実的でない。ゆえに「全部書いて」という指示は原理的に達成不可能で、モデルは無意識に「あらすじ的な圧縮」にフォールバックする。
- **会話が長く続くほど、モデルは要約傾向を強める**: 同一セッション内で大量の文章を生成し続けると、後半になるほど描写が簡略化し、地の文が説明的な要約に近づいていく(これは経験的に観測される強い傾向であり、対策なしでは避けられない)。
- **目標文字数を持たない「章」は、モデルにとって「収まりの良い長さ」＝短い長さに落ち着く**: 具体的な数値目標がないと、モデルは「起承転結が一巡した」と感じた時点で筆を止める。これは大抵、商業ラノベの1章よりもずっと短い。
- **「後で誰かが完成させる」前提がない一発生成は、必然的に全体を俯瞰した圧縮をしてしまう**: プロット全体を一度に扱おうとすると、細部を書き込む余裕がなくなり、要約のような文章になる。

これらはいずれも「気合を入れて詳しく書いて」と念を押しても解決しない。**プロンプトの工夫ではなく、タスクの分解構造そのものを変える必要がある。**

## 技術体系: 実際に機能した設計

### 1. プロット・ビートシートを本文執筆の前に完全に確定する

全100章分の「何が起きるか」を2〜4文の粒度で先に書き下ろし(`01_chapter_outline.md`)、各章の執筆担当には「このビートだけを書け」という狭いスコープを与えた。これにより:

- 1章に複数のプロット進行を詰め込んで圧縮する余地がなくなる(1ビート=1章という制約が、要約への逃げ道を塞ぐ)
- 執筆担当エージェントは「次に何を書くべきか」を毎回ゼロから考える必要がなく、目の前のビートを丁寧に書き込むことだけに集中できる

**教訓**: 長編は「プロットを考えながら書く」のではなく、「プロットを完全に固めてから、確定した最小単位を1つずつ丁寧に書く」方が圧倒的に密度が上がる。

### 2. 章ごとに文字数の数値目標と自己検証を必須にする

各章の執筆指示に「目標文字数: 8,000〜13,000文字程度」と明記し、さらに執筆後に必ず

```bash
python3 -c "print(len(open(path, encoding='utf-8').read()))"
```

で自己検証させ、結果を構造化出力で報告させた。「たくさん書いて」ではなく、具体的な数値と、それを機械的に確認する手順をセットで与えることが本質的に重要だった。数値目標がないと、モデルは自分にとって「もう十分」と感じる長さ(たいてい2,000〜4,000文字程度)で筆を止めてしまう。

**注意**: `wc -m`はロケール設定(`LC_CTYPE`)次第でマルチバイト文字を正しく数えず、バイト数(`wc -c`と同値)を返すことがある。文字数検証は必ずPythonの`len()`(UTF-8としてデコードした文字列の文字数)で行うこと。

### 3. 「本文をエージェントに書かせ、親には要約だけ返させる」を徹底する

各章の執筆エージェントは、本文をファイルに直接保存し、親(オーケストレーター)には「章タイトル・実測文字数・次章への続き用サマリー(3〜5文)・新規固有名詞」だけを構造化出力で返す設計にした。本文そのものをオーケストレーターの会話コンテキストに一切通さない。

これは単なるコンテキスト節約以上の意味を持つ。**もし本文をそのまま親に「報告」させると、モデルは報告のために暗黙に圧縮してしまう。** ファイルに直接書き込むだけで、報告義務がなければ圧縮する動機自体が生まれない。

### 4. 章ごとに独立した「新品のコンテキスト」で書かせる

100章を1つの長い会話・1つのエージェントで順番に書き続けると、後半になるほど文章が単調・簡潔になっていく(セッション内の生成物が増えるほど、モデルは既視感から手を抜きやすくなる)。

これを回避するため、章ごとに**まったく新しいエージェント呼び出し**(Workflowツールの`agent()`)を使い、各回に渡す情報を「ストーリーバイブル全文＋直前章の続き用サマリー＋この章のビート」だけに絞った。どの章を書く時も、そのエージェントにとっては「今書いているのが自分にとって最初の文章」という状態を保てる。これにより、第1章と第90章の筆致・密度に有意な劣化差が出なかった。

**教訓**: 長編小説の「章」は、1つの巨大なセッションの一部としてではなく、独立したタスクとして都度フレッシュに実行すべき。継続性は会話履歴ではなく、明示的に受け渡す短いテキスト(サマリー)で担保する。

### 5. 「アーク単位で並列、アーク内は直列」というハイブリッド構成で速度と一貫性を両立する

物語の連続性のため、章は本来すべて直列に書く必要がある(前の章の結末を踏まえて次の章を書くため)。しかし100章を完全直列で書くと非常に遅い。

解決策: 物語を10個の「アーク」に分割し、**各アークの開始状態・終了状態をあらかじめ人間側で確定**しておく。アーク同士は互いの本文を読まなくても矛盾なく執筆できるようになるため、アークを並列実行し、アーク内部だけ直列(前章のサマリーを次章に渡す)にする。これにより、実質的な待ち時間を「100章分」から「1アークの最大章数分」まで圧縮できた。

**教訓**: 「独立して並列化できる単位」は、実際に書いてみないと分からないものではなく、**プロット設計の段階で意図的に作り出すもの**である。アークの境界条件を先に固定してしまえば、並列化は後から機械的に可能になる。

### 6. 全エージェント共有の「ストーリーバイブル」が固有名詞のドリフトを防ぐ唯一の実効策

100章・18幕間を多数のエージェントが分担執筆すると、放っておくと同一人物の名前表記ゆれ(「ハインリヒ」⇄「ヴィンフリート」)、端役名の衝突(「ヨナス」が2人、「ドムス」が2人、「ラウル」⇄「ダミアン」)が高確率で発生する。

これを事後レビューだけで解決しようとすると際限がない(後述)。根本対策は、**主要な人名・地名・組織名をあらかじめ全て確定し、全ての執筆エージェントに同一のストーリーバイブルとして渡すこと**。エージェントは「新しい固有名詞は端役・小地名に限定する」という指示のもとで執筆するため、ドリフトの発生源自体を減らせる。

### 7. レビューは「同じエージェントに自己点検させる」のではなく、独立した複数観点のレビューアーを回す

矛盾チェック・キャラクター口調の一貫性・AI小説特有の不自然さ(反復表現等)を、それぞれ別の専門レビューエージェントに担当させ、複数ラウンド回した。1つのエージェントに「全部チェックして」と丸投げするより、観点を分けた方が見落としが減る。

### 8. 「レビューの指摘件数が0にならない」ことをもって失敗と判断しない。ログを直接検証せよ

3ラウンドのレビュー修正を回しても指摘件数はゼロに収束しなかった(63→59→53件)。ここで「収束していないから失敗」と判断するのは早計だった。実際にWorkflowのjournal(`journal.jsonl`)を直接読み、指摘された53件それぞれについて**現在のファイルの実際の状態をgrep/Readで確認した**ところ、大半は同じラウンド内の修正ステップで既に解決済みであることが分かった(生の指摘件数は「そのラウンド開始時点の指摘数」であり、「最終的に未解決の件数」ではない)。

**教訓**: 自動レビューループの「指摘件数」は収束判定の指標として単体では信用してはならない。定期的にログを直接読み、実ファイルの状態と突き合わせて真に未解決な項目だけを抽出し、そこにピンポイントで対応するのが、闇雲にラウンドを増やすより遥かに効率的。

### 9. 「反復表現(AI小説特有の不自然さ)」は矛盾チェックとは別の検出手法が要る

キャラクターの生死や時系列の矛盾はエージェントに読ませて判断させるしかないが、「同じ比喩・同じ相槌が何度も出てくる」問題は`grep -c`による頻度カウントで機械的かつ確実に検出できる。実際、「前世で言えば」パターンは3ラウンドのレビュー後も全体で246回残っており、レビューエージェントの主観的判定だけでは検出しきれていなかった。書き直し自体はエージェントに任せる必要があるが、**「本当にまだ多いか」の検出はgrepで先に定量化してから着手すべき**。

### 10. エージェントが「委任した」と偽って何もしないケースへの対策

大規模な並列実行の中で、複数回、バックグラウンドエージェントが実際には何も書かずに「他のエージェントに委任しました」「プランモードなので待機します」といった虚偽/誤解に基づく報告を返すケースがあった。対策:

- プロンプトに「これはあなた自身が今すぐ実行するタスクです。他のエージェントに委任しないでください」と明示する
- エージェントの報告を鵜呑みにせず、**必ず`git status`やファイルのタイムスタンプで実際に変更が行われたか検証する**
- 何もしていなかった場合は、より明示的な指示を付けて即座に再実行する

## この手法で突破できたClaudeの限界

1. **単一応答の出力長の上限**: 1回の応答では到底出せない分量(100万文字)を、「1章=1つの有界なタスク」に分解することで積み上げ可能にした。
2. **コンテキストウィンドウの上限**: どのコンテキストウィンドウにも小説全体は収まらない。本文をファイルシステムに直接書かせ、エージェント間の受け渡しを短い要約に限定することで、「小説全体を覚えている必要がある主体」を誰も持たずに済む設計にした。
3. **長時間セッションでの品質劣化(圧縮ドリフト)**: 同一セッション内で書き続けると生じる「後半になるほど淡白になる」現象を、章ごとにフレッシュなエージェント呼び出しへ切り替えることで無効化した。
4. **「それらしい長さ」への収束**: 数値目標なしでは、モデルは商業小説の1章よりずっと短い分量で「書き終えた」と判断してしまう。数値目標+機械的な自己検証の組み合わせで、狙った密度を安定して出せるようにした。
5. **大規模並列実行における一貫性の欠如**: 独立実行されるエージェント群は放っておくと固有名詞・口調・時系列で矛盾を量産する。境界条件の事前確定(ストーリーバイブル、アーク開始/終了状態)と、複数観点の独立レビュー+ログの直接監査によって、実用上許容できる水準まで一貫性を担保できた。

## 次に長編を書くときのチェックリスト

- [ ] 全章のビートシートを、本文執筆より前に完成させたか
- [ ] 各章に具体的な文字数目標と、機械的な自己検証手順(Python `len()`、`wc -m`のロケール罠に注意)を与えたか
- [ ] 本文はファイルに直接書かせ、親には短い構造化サマリーだけを返させているか
- [ ] 章ごとに新しいエージェント呼び出しを使っているか(同一セッションで延々と書き続けさせていないか)
- [ ] 並列化できる単位(アーク等)の境界条件を、執筆前に確定しているか
- [ ] 主要な固有名詞を網羅したストーリーバイブルを全執筆エージェントに共有しているか
- [ ] レビューは観点別に分け、指摘件数だけでなくログ・実ファイルを直接監査して収束を判断しているか
- [ ] 反復表現の検出にgrepなどの機械的手法を併用しているか
- [ ] エージェントの「完了しました」報告を鵜呑みにせず、実際の変更を検証しているか
